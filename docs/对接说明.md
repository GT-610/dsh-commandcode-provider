| 双方都没有 | 配置与凭据的跨服务原子事务、对在途请求追溯改写配置 |

1. **准入声明改为同通道区间。**`dsh.compatibility.dshReleases` 两条记录 `0.2.1-rc.2` 与 `0.2.1-rc.3`（都是 RC），`dsh.compatibility.dsh`、`engines.dsh` 与 15 个 peer／19 个开发依赖同为 `>=0.2.1-rc.2 <0.2.2-0`；上界带 `-0` 是因为按 semver 优先级 `0.2.2-rc.1 < 0.2.2`，写成 `<0.2.2` 会放行下一个 minor 的 RC。`0.2.0-rc.2` 已退出 npm `latest` 并落在区间之外，alpha 通道不保留。宿主判定语义未变（自 `0.2.1-alpha.4` 起只读 `engines.dsh`，`semver.satisfies` 带 `includePrerelease: true`）。理由与代价见[《决策记录》第八章第16条](决策记录.md#八dsh-引擎兼容范围与验证边界)。
2. **Cordis 与 Schemastery 收敛为单分支。**rc.2 与 rc.3 的 vendor 实测都是 `cordis 4.0.5` / `schemastery 3.18.5`，两引擎配对相同，故写 `~4.0.5` / `~3.18.5`；上一轮的 `~4.0.4 || ~4.0.5` / `~3.18.4 || ~3.18.5` 只为覆盖已退出的 `0.2.0-rc.2` 配对。这两个名字不匹配 `@deepseek-ai/dsh*` 前缀、宿主准入不读它们，差异只在 pnpm 解析层生效。
3. **rc.3 没有运行代码破坏点。**宿主准入语义（`packages/boot/app-boot/src/plugin-compatibility.ts`）与 Web 预置模块表（`packages/client/web/src/seed.ts`）相对 rc.2 逐字相同；插件导入的宿主包在 646 个变更路径里没有源码级改动。本轮故障完全来自声明面（`engines.dsh` 未覆盖 rc.3）。上一轮为兼容 pre-rc.2 引擎加的网页搜索「实例字段形状」分派随之删除，只留易变引用路径，见第五章第 2 条。
4. **五个既用插槽全部保留，rc.3 只做新增。**`settings.section`、`settings.models.provider-card`、`main`、`sidebar.footer.action`、`conversation.composer.dock` 的声明未变；新增的 `sidebar.panellist.actions`、`conversation.session.header.views.actions`、`sidebar.right.tab.guide.actions` 三个 list 类插槽与插件 id／key 无冲突。`dsh-client-ui-primitives` 的导出符号集合逐个相同（`Menu`／`StateDot`／`MenuEntry`／`StateDotState`／`Button` 全在）。
5. **打包与客户端面未变。**Web 预置模块表逐字相同，`lib/client.js` 的三个 `require()` 目标（`react`、`react/jsx-runtime`、`@deepseek-ai/dsh-client-ui-primitives`）仍全在表内；`dsh.client.inject` 的三个包名仍存在，语义仍是「boot 图前置依赖」而非服务注入列表；`dsh.client.platform`、`exports["./client"]`、`dsh.bundle.patch` 的解析契约均未变。
6. **rc.2 首发的两个官方包仍在，无冲突。**`web-deepseek-api` 的搜索提供方 id `deepseek-search-api` 与插件的 `commandcode` 不同（`registerSearchProvider` 只在 id 重复时抛 `WEB_DUPLICATE_PROVIDER`）；`conversation.input.model.label` 是 `single`（单占）类插槽，插件不得注册任何贡献。
7. **rc.3 新增的浏览入口定制不接入。**`ui-entry-customization` 与两处「更多」菜单属于官方客户端的界面能力，插件不注册这些新插槽；是否接入留待出现实际需求时单独评估。
